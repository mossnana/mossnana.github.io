Mental Model สำหรับวิศวกรทดสอบประสิทธิภาพ (Performance Testing)

ทำไมต้องตั้งค่า Scenario, Executor และ Stage ให้สัมพันธ์กัน?

ในการจำลองทราฟฟิกเข้าสู่ระบบ (Load Testing) ถ้าเปรียบการทดสอบเป็น "การจัดขบวนรถวิ่งบนทางด่วน" ทั้ง 3 ส่วนนี้คือลำดับชั้นที่สั่งการกันโดยตรง ลองคลิกที่แต่ละกล่องด้านล่างเพื่อดูหน้าที่และความเชื่อมโยง

โครงสร้างลำดับชั้น (คลิกเพื่อไฮไลต์ความสัมพันธ์) options.scenarios
1

Scenario (ฉากจำลองพฤติกรรม)

กรอบใหญ่สุด

เปรียบเสมือน "ภารกิจของผู้ใช้กลุ่มหนึ่ง" เช่น กลุ่มคนเข้ามาส่องสินค้า vs กลุ่มคนกดสั่งซื้อ Flash Sale

2

Executor (เครื่องยนต์ปล่อยโหลด)

1 Scenario มี 1 Executor

เปรียบเสมือน "ระบบเกียร์ของเครื่องยนต์" ที่กำหนดว่าจะปล่อยโหลดด้วยวิธีคุม จำนวนคน (VUs) หรือคุม อัตราความเร็ว (RPS/Arrival Rate)

3
Stages (สเต็ปการเร่ง/ผ่อนตามเวลา)
ใช้เฉพาะ Ramping Executor!

เปรียบเสมือน "คันเร่งและเบรกตามช่วงเวลา" เช่น ค่อยๆ เหยียบคันเร่งไปที่ 100 คนใน 1 นาที แล้วแช่ไว้ 3 นาที

กฎเหล็กที่ต้องจำ: คุณจะตั้งค่า stages: [...] ได้ ก็ต่อเมื่อ เลือก executor ตระกูล Ramping (ramping-vus หรือ ramping-arrival-rate) เท่านั้น! หากใช้ Executor แบบคงที่ (Constant) จะใช้การกำหนดค่า duration คู่กับ vus หรือ rate แทน

                    Cheat Sheet สรุปการจับคู่
                

                
ตารางสรุป Executor ทั้ง 6 ตัว: ตัวไหนต้องใช้ Stage? ตัวไหนเหมาะกับงานอะไร?

                
คลิกปุ่ม "ลองในกราฟ" ในตารางเพื่อโหลดค่าตัวอย่างขึ้นไปแสดงบนกราฟด้านบนทันที

            


            

                

                    

                        
                            

                                ชื่อ Executor
                                โหมดการควบคุม
                                ใช้ stages ได้ไหม?
                                พฤติกรรมการทำงาน
                                เหมาะกับสถานการณ์ใด?
                                ทดลอง
                            

                        
                        
                            

                                ramping-vus
                                คุมจำนวนคน (VUs)
                                ใช้ Stages
                                ปรับเพิ่มหรือลดจำนวน VUs ขึ้นลงตามช่วงเวลาที่กำหนดในแต่ละ Stage
                                Load Test ปกติ, Stress Test ขั้นบันได, หรือ Spike Test จำลองคนทะลักเข้าเว็บ
                                
                                    
                                
                            

                            

                                ramping-arrival-rate
                                คุม RPS / อัตราเข้า
                                ใช้ Stages
                                ปรับเพิ่มหรือลดอัตราการยิง (Iterations/วินาที) ตาม Stage โดยไม่สนว่าระบบจะตอบช้าหรือเร็ว
                                ทดสอบ API Gateway หรือระบบชำระเงินที่ต้องการวัด Throughput (RPS) ที่ค่อยๆ พุ่งสูงขึ้น
                                
                                    
                                
                            

                            

                                constant-vus
                                คุมจำนวนคน (VUs)
                                ไม่ใช้ (ใช้ duration)
                                ปล่อย VUs จำนวนคงที่แช่ไว้ตั้งแต่ต้นจนจบเวลา duration
                                Smoke Test เช็คระบบเบื้องต้น หรือ Soak Test แช่โหลดนิ่งๆ ดูอาการ Memory Leak
                                
                                    
                                
                            

                            

                                constant-arrival-rate
                                คุม RPS / อัตราเข้า
                                ไม่ใช้ (ใช้ rate + duration)
                                ยิง Request ด้วยความเร็วคงที่ (เช่น 50 รอบ/วินาที) ตลอดระยะเวลาที่กำหนด
                                ทดสอบ SLA ของ Microservice ที่การันตีว่าต้องรับโหลดได้คงที่ เช่น 100 RPS
                                
                                    
                                
                            

                            

                                per-vu-iterations
                                คุมจำนวนรอบ (Iterations)
                                ไม่ใช้ (ใช้ iterations)
                                กำหนดให้ VU แต่ละคนรันสคริปต์จนครบจำนวนรอบที่ตั้งไว้แล้วหยุดทันที
                                ทดสอบการสร้างข้อมูล (Data Seeding) เช่น มี Test User 10 บัญชี ให้แต่ละบัญชีสร้างออเดอร์คนละ 5 รายการ
